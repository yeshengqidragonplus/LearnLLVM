## 三、根因诊断（决定性证据）

### 证据 1：纯复制探针
```
问: 抄写 4483\n答:   → 4483   ✅ 4 位
问: 抄写 94692\n答:  → 9492   ❌ 5 位丢位（第 3 位 6 消失）
```
**连"抄写"这个最简单任务，5 位就做不到**——复制通道是**定宽电路**（训练 1~4 位 → 只能复制 4 位）。

### 证据 2：数位数失败的机制
```
问: 94692 是几位数?
→ 理解: 数列 L := 9,4,6,2     ← 第 1 步就丢位（5 个数字只抄了 4 个）
→ 计数: i=1(9), i=2(4), i=3(6), i=4(2)   ← 计数逻辑完全正确
→ 答: 4                        ← 但基于错误的输入
```
**数位数的计数逻辑是对的，但它的输入（数列）已经错了**——所以数位数没能破墙：
**它的第一步就是复制**，被复制墙挡住。

### 证据 3：序关系退化的机制
```
问: 1619<1629?（应 ⊤）
→ 尝试: s(1619)=1620, ..., s(1622)=1623（继续只会更大）   ← 用了 v4 新增的"a>b"模板
→ 判断: 从 a=1619 出发单调递增，无法到达**更小的** b=1629   ← 逻辑错乱
→ 答: ⊥
```
v4 新增的 `a>b` 模板被**错误套用到 `a<b`**——所以 v3 的 ⊤ 从 100% 掉到 33%。

### 修正假设（诚实）
之前判断"根因 = 位数不可知"**不完整**。真实结构是三层：
```
表象：位数不可知（循环上界 k 输出错）
  ↑
中层：绑定行复制丢位（数列 L := 9,4,6,2）
  ↑
底层：复制/读取通道是【定宽电路】——训练 1~4 位就只能复制 4 位
```
这是旧系列 v8"定宽电路"在新系列的重现。

## 五、v5 方向（用户原设计：化简不搬运）

用户原设计（2026-09-17 提出，被 v3/v4 偏离）：
> "先把数字简化成 a 或 x 这样代数，**整个输入的语句先做一遍处理**，化简成最简语义，
> 然后再渐进展开"

**关键修正**：化简步**不应搬运数字**（那是复制）。应"绑定符号 + 逐位查读"：
```
问: 112+522222 = ?
理解: 算式 F, F := a+b（a 为输入第 1 串，b 为第 2 串）   ← 不写数字！
算法: i 从 1 起，从右往左读 a_i 与 b_i，直到两串都取完   ← 结构性停止条件
i=1: a_1=2, b_1=2, 2+2+0=4, 写4进0
...
i=4: (a 已取完), b_4=2, 0+2+0=2, 写2进0
结束: 两串均已取完
```
**三个关键**：
1. 没有任何一行写完整数字（`a_1=2` 是一次一位的读取）
2. 停止条件是结构性的（"直到两串取完"）→ **绕开"位数不可知"**
3. `(a 已取完)` 显式化越界（非隐含循环上界）

**风险**：位置查读（attend to position i）能否跨长度泛化——v4-A 不能证明不行
（查读从未被单独训练）。**需 v5 专门训练验证。**

## 三、根因分析

### 核心发现：**墙从"复制丢位"转移为"位数不可知"**

v1/v2 的墙：注意力一次性复制 N 个数字 token → 丢最高位。
v3 把复制改成逐位了（`x := 9,7,4,4,3`），**复制不再是瓶颈**——但出现了新的墙：

```
【5位后继】prompt = 问: s(97443) = ?
模型输出:
  理解: 算式 F, F := s(x), x := 9,7,4,4          ← 只有 4 个数字！（应 5 个）
  算法: 后继公理 s(x)=x+1：i 从 1 到 4 循环        ← 循环上界 4！（应 5）
  i=1: x_1=4, c=1, s_1=4+1=5, d_1=5, c:=0        ← 后续执行全对
  ...
  合成: 9,7,4,5
  答: 9745                                        ← 错（应 97444→97445）
```

**同一个病在三处复发**：

| 用例 | 模型输出 | 应为 |
|---|---|---|
| `s(97443)` | `x := 9,7,4,4` / `i 从 1 到 4` | 5 个 / 到 5 |
| `10561+914` | `a := 1,0,5,6` / `i 从 1 到 4` | 5 个 / 到 5 |
| `38310 =` | `三百八十三`（丢"三万八千"） | 三万八千三百一十 |
| `s(s(1400))` | `x=1,4,0,0` → `第一步: s(140)=141` | 1400 |

**结论**：
1. 循环格式的**执行机制是对的**（4 位内 100%）——迭代、进位传递、合成全部正确
2. **但循环的上界 `k` 输出错了**——`i 从 1 到 k` 需要知道 k=5，模型只会输出 1~4
3. **"位数"从未被显式训练过**——它是训练数据里的**隐含属性**（1~4 位随机采样，模型没学到"数位数"这个动作）

**为什么 v3 的循环格式没能破墙**：循环格式解决的是"每步宽度 1"（避免一次性复制），但它**假定了 k 是已知的**。而 k（位数）本身也需要一个算法——**数位数**。

### 问题 2：序关系方向语义丢失（独立问题）

```
【a>b 应 ⊥】prompt = 问: 5503<5497?
模型输出:
  步数: s(5497)=5498, ..., s(5502)=5503     ← 自动从 min（5497）数到 max（5503）
  判断: n=6≥1，可达
  答: ⊤                                      ← 错！应为 ⊥

【a=a 应 ⊥】prompt = 问: 490<490?
  步数: s(490)=491, ..., s(497)=498          ← 编了 8 步（490 数到 498，与 490 无关）
  答: ⊤                                      ← 错
```

模型学成了**"两数不同就可达"**：它自动从 min 出发数到 max，然后答 ⊤。
定义 `a<b ⟺ ∃n≥1, sⁿ(a)=b` 里"**必须从 a 出发**"这个约束丢了。

**根因**：训练数据里"从大的数出发"的情形**从未出现**——因为生成器在 `order_chain(a,b)` 内部用 `lo,hi = min,max` 统一从小的数起数。模型没见过"从 5503 出发数不到 5497"的样本。

**注意**：这不是样本量问题（⊤1736 / ⊥1810 充足），是**教学方式**问题——⊥ 样本虽然多，但它们的"步数链"都是从 min 出发的，模型学到的模式是"数到为止 → 可达"。

## 五、工程突破：OOM 根因与解法（可复用）

### 现象
v3 训练连续 3 次 OOM（batch=32 / 24 / 16 都爆）。

### 排查过程（实测数据）
1. 先怀疑 8/9 位锚点太长 → **实测否定**：8/9 位仅 4 条，4 位加法 4305 条才是主体
2. 实测 token 长度：**v3 4位加法中位 305 vs v2 188**（循环格式每行多了 `i=`/`c=`/`s_1=`/`d_1=`/`c:=`）
3. 显存估算：`batch × seq × vocab(151646) × 4B`（HF 把 logits 升 fp32）
   - v3: `16 × 305 × 151646 × 4 = 2.96GB`（**单是 logits fp32**）+ bf16 1.48GB = 4.4GB
   - v2: 只有 1.82GB → 所以 v2 batch=16 安全

### 精度实测（回答"能否用 bf16 省显存"）
| 方案 | 梯度相对误差 | 结论 |
|---|---|---|
| fp32（HF 默认） | 0%（基准） | 数值稳定 |
| **bf16 输入** | **1.35%** | 有代价，训练几万步会累积 |
| fp16 输入 | — | 范围小（±65504），需 loss scaling |

### 解法：分块 fp32 loss（数学等价，非近似）
```python
# 原理：交叉熵 = 逐 token 求和，可分块累加
hidden = model.model(input_ids).last_hidden_state
for i in range(0, L, 64):
    logits_c = model.lm_head(hidden[:, i:i+64]).float()   # 仅本块升 fp32
    loss += F.cross_entropy(logits_c.reshape(-1,V), y_c.reshape(-1),
                            reduction="sum", ignore_index=-100)
loss = total_sum / total_cnt      # 与 HF mean 等价
```
- 峰值 logits 从 `(16,305,151646)` = 2.96GB 降到 `(16,64,151646)` = 0.62GB
- **对拍验证**：`HF 原生 = 12.048318 | 分块 = 12.048318 | 相对差 0.0000%` ✅
- 附带收益：**提速**（1.55h vs 预估 7h）——省掉巨型张量的反复分配/搬运

### 新增脚本参数
`--loss-chunk 64`（分块大小，0=HF 原生）、`--verify-loss`（对拍验证，相对差 >0.1% 拒绝训练）

### 一个需要思考的设计问题
"数位数"如果要**宽度无关**（能数 20 位），它自己也需要循环：
```
数位: 9,7,4,4,3
计数: i=1(9), i=2(7), i=3(4), i=4(4), i=5(3)   ← 循环个数 = 位数
答: 5
```
这与加法循环同构（i 递增直到数字串结束）。**但"直到结束"需要一个停止条件**——模型要学会"看到绑定行有 5 个数字就数到 5"。这是下一个要攻克的机制。
