## 0. 第一稿的两个错误

| # | 错误 | 后果 |
|---|---|---|
| E1 | L1 选例用了 `1234567 + 7654321` | 那是 09 号单列专家已实测通过的案例（`output_iterative_digit_v1`，200/200 状态穷举、100 位全 9 加 1 正确）。重复做不产出新信息 |
| E2 | 自造 `H1`/`H4` 句柄，未沿用 `<|PKG_*|>` 标记族 | 丢了类型（`H1=数` 要靠文本学；`<|PKG_NUM|>` 一个 token 就是类型），且缓存/投影/解包规则另起一套，与 20 号已跑通的解包审计不兼容 |
| E3 | 把"科室"当成外挂执行器，说"基座权重不动" | **错误。** 科室是**从基座继续训练出来的独立模型权重**（医生），不是给基座外挂插件 |
| E4 | 反过来把执行器排除在科室之外，纠结"09 算不算医生" | **也不对。** 执行器就是路由结果的一种，像做 CT / 核磁——**必要、简单、写个工具就行，不是研究重点**。协议只要求"路由目标"统一，不要求所有目标都是模型 |

两处错误的同一个后果：**把"基座该做什么"和"科室该做什么"压成一层**。于是动作表既想管问诊（ASK/OUTPUT），又想管科室内部算路（COMPUTE/CHECK），还漏了最关键的**挂号**（ROUTE）。

## 1. 核心修正：基座是"人"，科室也是"人"，不是"工具"

### 1.1 分层不是在基座上叠插件

**正确模型**：

```
                    沟通交流基座（一个模型）
                   /        |         \
              续训         续训        续训
                /            |           \
        门诊医生         声明科医生     算数科医生
        (ASK/ROUTE)      (GEN_DECL)    (COMPUTE)
```

每个医生 = **从同一个基座继续训练得到的独立权重**。他们共享出身（同一个基座、同一套 Package 协议），但各自是完整的模型，能自己理解、自己判断、自己出动作、自己生成结果。

**不是**"基座权重冻结 + 外挂 Python 函数"。这一点第一稿写错了，纠正过来之后，协议设计的目标整个变了。

### 1.2 那么两层的动作表还在不在？在，但含义变了

| 层 | 谁的动作 | 内容 | 性质 |
|---|---|---|---|
| **基座层** | 门诊医生的动作 | ASK / ROUTE / SPLIT / MERGE / VERIFY / OUTPUT / DONE / FAIL（8 个） | 是"分诊与编排"，不是"治病" |
| **专科层** | 各科室医生自己的动作 | 声明科：GEN_DECL / EXPLAIN_DECL；算数科：COMPUTE / CHECK；… | 是"干活"，各医生自己训练出来 |

基座层的 8 个动作**是所有医生共用的公共词汇**（因为所有医生都从同一基座续训，都继承这套词）；专科动作是各医生在续训时新学的能力。

### 1.3 协议存在的真正理由（这条是这次纠正后浮现的）

第一稿以为协议是为了"程序能解包"。真正的理由是：

> **不同权重的模型之间要能交接，就必须共享同一套 Package 格式与动作标记。**

门诊医生 ROUTE 给声明科医生时，声明科医生看到的是门诊医生写下的包引用 `<|PKG_CODE|>#1`。这两个模型是**两份不同权重**，能读懂对方写的东西，唯一的保障就是它们都从同一基座续训、都用同一套标记。

所以协议 = **模型间的通信标准**，不是程序接口。这是它比任何单模型能力都更基础的原因：能力可以慢慢加，格式一旦各写一套，会诊就不可能成立。

### 1.4 对工程的三条直接推论

| # | 推论 | 依据 |
|---|---|---|
| C1 | 每个医生词表 = 基座词表 + 自己新增的专科标记，需要 `--resize-embeddings` | 03 已支持；声明科 3 个标记、算数科 2 个、门诊 8 个 |
| C2 | **基座动作标记必须在所有医生词表里都存在且同 ID** | 否则门诊写的 `<|ROUTE|>`，声明科读成另一个 ID，交接立刻失效 |
| C3 | 续训会破坏基座的交流能力，必须逐医生测遗忘 | 这正是 todo 里"两个专家回归测数学少量样"的真正意义所在，而且现在要测的是**交流能力**保留了多少 |

**C2 是一条硬约束**：所有医生的新标记必须用同一张全局标记表统一分配 ID，不能让各医生自己随意 resize。建议实现成一份 `tokens.json`（标记名 → ID），所有续训脚本从它读。

### 1.5 路由目标有两类：医生 与 执行器

两者在协议里**地位相同**，都只是 ROUTE 的对端，区别只在实现方式：

| 路由目标 | 是什么 | 例子 | 是不是研究重点 |
|---|---|---|---|
| **医生** | 从基座续训的独立权重 | 声明科医生、门诊医生 | **是**（这是这套架构的核心假设） |
| **执行器** | 一个普通程序/工具 | 整数加法、进制转换、CT 设备 | **不是**，写个工具就行 |

**这条消除了一个伪问题**：不需要纠结"09 的 8,260 参数 MLP 算不算医生"。它就是执行器，和进制转换一样，路由到它、它返回结果、完事。协议不关心对端是模型还是程序。

## 1.6 那么"怎么训练模板"才是真问题

用户即将重新训练沟通交流基座，v5c1 不再作为前提。模板能力要在一个新基座上训练，问题变成：

### 训练数据从哪来（这是模板训练的唯一难点）

真实任务不可穷举，所以**不能手写模板**。但可以自动生成轨迹，机制是：

```
科室能力表（声明式）
  声明科：输入 <|PKG_CODE|>  →  输出 <|PKG_NUM|>, <|PKG_NUM|>
  算数科：输入 <|PKG_NUM|>×2  →  输出 <|PKG_NUM|>
  进制转换：输入 <|PKG_NUM|>  →  输出 <|PKG_TEXT|>

目标包类型：<|PKG_TEXT|>（十六进制文本）
        ↓ 反向搜索能力表
进制转换 ← 算数科 ← 声明科 ← <|PKG_CODE|>
        ↓
轨迹骨架自动得到，换参数即实例化成海量样本
```

**关键**：轨迹不是手写的，是**从"目标包类型"在能力表上反向搜索出来的**。这就是"真实世界复杂但不用手写模板"的落地机制——能力表加一行，所有能用它拼出的任务都自动获得训练数据。

### 训练数据长什么样

每条轨迹切成 N 条「投影 → 动作行」样本（§4 的投影格式），用 `--target-mask --no-pack`，target 只有 5–10 token 的静态标记。

### 训练四步（顺序不能反）

| 步 | 做什么 | 为什么必须这一序 |
|---|---|---|
| **1** | 写**规则脑** + 循环控制器（不含模型） | 规则脑跑不通 = 协议设计错了，此时训模型是白训 |
| **2** | 规则脑跑跑通后，自动导出轨迹数据 + 审计 | 数据由已验证的正确路径生成，不引入错误标注 |
| **3** | 训模型模仿规则脑（每步一条，target-mask） | 有明确 teacher，判据可自动算 |
| **4** | 用模型替换规则脑，同条件对比逐轮正确率 | **唯一能证明"模型学会了"的对照** |

第 1 步是最容易被跳过的一步，但它决定后面全部。20 号数据能到 920 条审计全过，正是因为它先有确定性生成器、再谈训练。

### 判据（全自动）

| 指标 | 定义 |
|---|---|
| 逐轮正确率 | 单步 投影→动作 是否正确（可定位到"动作错/参数错/包不存在"） |
| 整条全对率 | 一条轨迹 N 轮全对（≈ 逐轮正确率 ^ N，所以要求单轮很高） |
| 与规则脑差距 | 模型 vs 规则脑在同一批任务上的差值 |

**注意**：多轮会放大误差。N=5 时单轮 95% 只剩 77%。所以模板训练的目标不是"能用"，是把单轮正确率推到 99% 以上。

## 1.7 模板**不**理解语义——这是它成立的前提，不是它的缺陷

这一条必须写清楚，否则会被误当成"模板能理解所有语义"。

| 谁负责 | 做什么 | 例子 |
|---|---|---|
| **交流层**（基座） | 理解用户原话，把模糊表达变成结构化输入 | "那两个数" → 指出是哪两个 → 前端打包成 `<\|PKG_NUM\|>#2 #3` |
| **模板层**（本协议） | 拿着已经打包好的结构，决定下一步做什么 | 看到 `<\|PKG_CODE\|>#1` → `<\|ROUTE\|> #1 声明科室` |

**模板看到的从来不是用户原话，是已经打包好的结构。** 这就是声明数据能到 58/60 的原因：模型看到的 prompt 是

```
<|PKG_CODE|>
语言=C
载荷：static const unsigned int CAP = 26162U;
原子包：<|PKG_NAME|> → CAP；<|PKG_NUM|> → 26162U
```

不是"帮我把 CAP 改成常量"。它不需要理解中文语义，只需要做格式转换。

### 三条推论

| # | 推论 |
|---|---|
| 1 | **模板能力可以在没有交流能力时单独训练和验证**——它不需要基座会聊天 |
| 2 | 模板能处理的任务范围 = 前端能打包出的结构范围。前端打包不了的原话，模板根本看不到 |
| 3 | "模板理解所有语义"这个目标不该追求。真正要追求的是：**前端打包覆盖度** + **交流层澄清能力** |

第 2 条是最实际的约束。现有前端只能用正则处理"代码围栏/反引号/简单 C 声明/数字加法"。它处理不了：

- 指代（"那两个数"、"上面那个"）
- 省略（"再来一次"、"换成十六进制"）
- 歧义（"改一下"——改什么、改成什么）
- 多轮上下文（"就按刚才说的做"）

**这四类正是交流层的活**，不是模板层的活。所以"7 个动作够不够"这个问题的真正答案取决于"前端能打包出多少种结构"，而不是"世界有多少种任务"。

## 2. 基座层 8 个动作（"够不够"要怀疑的只有这 8 个）

| 标记 | 语义 | 参数 | 取值域 |
|---|---|---|---|
| `<|ASK|>` | 追问缺失信息 | 槽位名 | 封闭槽位表 |
| `<|ROUTE|>` | 挂号：把包交给某科室 | `<|PKG_*|>#n` + 科室名 | 注册表 |
| `<|SPLIT|>` | 拆子任务 | 子任务数 + 每项科室 | 注册表 |
| `<|MERGE|>` | 汇总多科室结果 | 若干 `<|PKG_*|>#n` | 包表 |
| `<|VERIFY|>` | 校验结果 | `<|PKG_*|>#n` + 校验器名 | 注册表 |
| `<|OUTPUT|>` | 交付用户 | `<|PKG_*|>#n` | 包表 |
| `<|DONE|>` | 结束 | 无 | — |
| `<|FAIL|>` | 无法完成 | 原因码 | 封闭码表 |

**ROUTE 是第一稿最大的遗漏。** 没有它，协议等于"程序自己知道该干什么"，模型不参与分诊——那就退回规则路由，和学习路由 63.9% 那个实验没有本质区别。

**SPLIT 为什么必须在基座层**：拆解需求是问诊的一部分（"帮我写个网站"要先拆成前端/后端/部署）。它不归任何科室。

**你怀疑 7 个不够，是对的。** 但不够的不是"操作的种类"，是"层"。第一稿把基座动作和科室动作混在一张表里，所以既缺 ROUTE，又塞进了本属科室的 COMPUTE/CHECK。分层之后，基座 8 个是完整的（问诊/拆分/挂号/汇总/校验/交付/终止两类），科室动作随科室增长。

## 3. Package 沿用你的设计（不新造句柄体系）

| 类型标记 | 载荷 | 生成器 |
|---|---|---|
| `<|PKG_ARITH|>` | 算术表达式原文 | 06 |
| `<|PKG_CODE|>` | C 代码区域 | code_package_frontend_v1 |
| `<|PKG_NUM|>` | 一个数值字面量 | 同上（嵌套原子包） |
| `<|PKG_NAME|>` | 一个标识符 | 同上（嵌套原子包） |
| `<|PKG_TEXT|>` | 一段自然语言 | **新增，待写** |
| `<|PKG_TASK|>` | 一个子任务 | **新增，待写** |

引用语法：`<|PKG_NUM|>#3`

- `<|PKG_NUM|>` 是已注册的单 token，**类型白送**
- `#3` 是会话内单调序号（2–3 token），只用于消歧
- 序号由程序分配，模型只能引用投影中出现过的

**相比第一稿 `H1` 的收益**：类型不用学、标记可复用、payload 规则与 20 号完全一致、20 号的解包与审计代码可直接复用。

## 4. 投影格式（逐字定稿，含 D6 改动）

```
[任务] ...
[轮] 3/32
[包] <|PKG_CODE|>#1 代码  <|PKG_NUM|>#2 数值(来自#1)  <|PKG_NUM|>#3 数值(来自#1)  <|PKG_NAME|>#7 科室
[日志] 1.<|ROUTE|> #1 #7; 2.<|ROUTE|> #2 #3 #8
[错误] 无则省略此行
[动作]
```

载荷永不进投影。`数值(来自#1)` 给的是来源，不是值；`#7 科室`是注册表里的一个科室条目。

**科室引用也走包引用**（D6 改动）：`<|PKG_NAME|>#7` 指向注册表里的"声明科室"。
好处是加科室只需注册表加一行，不用给每个科室注册新词表标记。

## 5. 一个不重复你旧实验的 L1

09 已证明「科室内部循环能处理任意位宽」（200/200 穷举、100 位全 9 加 1 正确）。所以 L1 不该再测循环，该测**从来没测过的**：**package 在科室之间传递**。

**用户原话**：`这段代码 const int A = 1234567; const int B = 7654321; 把这两个常量加起来，用十六进制告诉我`

**前端打包**（规则，已有）：`<|PKG_CODE|>#1`，payload 存缓存

| 轮 | 投影要点 | 模型输出 |
|---|---|---|
| 1 | `[包] <\|PKG_CODE\|>#1 代码` | `<\|ROUTE\|> #1 声明科室` |
| 2 | 多了 `#2 数值(来自#1) #3 数值(来自#1)` | `<\|ROUTE\|> #2,#3 算数科室` |
| 3 | 多了 `#4 数值(来自#2,#3)` | `<\|ROUTE\|> #4 进制转换` |
| 4 | 多了 `#5 文本(来自#4)` | `<\|OUTPUT\|> #5` |
| 5 | — | `<\|DONE\|>` |

三科室串联，**每步只有 ROUTE + 包引用**，模型全程不搬运数值。

三个路由目标的实现对协议没有影响（§1.5），可以全用执行器起步：

| 科室 | 起步实现 | 备注 |
|---|---|---|
| 声明科 | 20 号执行器（或 `output_decl_packed_v1` 医生） | 都有 |
| 算数科 | 09 的 200 状态执行器 | 已有 |
| 进制转换 | 一行 Python | 写起来最快 |

**L1 的判据只关心协议链路**：包是否被正确传递、ROUTE 是否选对科室。用执行器完全够，不需要先训医生。

**判据**：5 轮全对率 / 路由选择正确率 / 包传递丢失数。

### 5.6 实现时踩到的三个真实坑（写类似代码要避开）

| 坑 | 现象 | 根因与修法 |
|---|---|---|
| **聚合科被 BFS 剪掉** | 规划成"声明科→进制转换"，两个数根本没相加 | `num→num` 是 kind 自环，只按 kind 去重会剪掉它。改成**逐轮动态规划**：每轮只看下一步，聚合由执行时发现 |
| **tokenizer 未注册标记** | 量出的投影长度与边界校验全是假的 | `<\|OUTPUT\|>` 未注册时切成 5 个 token，注册后是 1 个。数据脚本必须先 `add_special_tokens` 再统计 |
| **`text` 字段多加换行** | 88 条全部报 `--target-mask` 边界不一致 | `text` 必须严格等于 `prompt + target`；prompt 已以换行结尾时再加 `\n` 就破坏拼接边界 |

## 7. 决策结果（2026-10-21 已确认）

### 7.1 D6 改动的理由：科室名与指示代词是同一个机制

原来 D6 建议"科室名写明文短名"，即 `<|ROUTE|> #1 声明科室`。用户指出：**已经有 `<|PKG_NAME|>` 了，科室名也应该走它。**

这个改动看起来只是措辞，实际上统一了两件原本分开的事：

| 现象 | 输出 | 本质 |
|---|---|---|
| "声明科室" 这个能力 | `<\|PKG_NAME\|>#5` | 指向注册表里的一个条目 |
| "这两个常量" | `<\|PKG_NUM\|>#2 #3` | 指向包表里的两个条目 |

**两者都是"指向一个已存在的对象"，所以用同一套引用机制。**

好处有三个：

1. **科室可动态增加**：加科室只需 `tokens.json` 加一行 + 注册表加一条，不用给每个科室注册新标记、不用改词表。如果科室名写明文，模型要学每个科室名的 token，加科室就等于改训练数据分布。
2. **输出空间封闭**：科室名从"任意中文词"缩小成"包表里的引用集合"，可以自动判分。
3. **和代词同构**（见 §1.8）：这说明代词消解不是额外的能力，**它和"引用一个包"是同一个操作**。

## 1.8 指示代词：必须单独测，且与 Transformer 架构强相关

用户指出的第一件事：**"靠交流层训练的指示代词，需要测试怎么才能学会，这跟 Transformer 架构本身有关系"**。这条要拆开说。

### 1.8.1 一个关键简化：代词消解的答案就是包引用

传统做法把指代消解当成"输出一个实体"的开放生成，无法自动判分。用包引用方案后，答案变成有限集合里的选择：

```
上下文：用户先说了 A = 1234567，又说了 B = 7654321
        前端已打包：<|PKG_NUM|>#1 = 1234567, <|PKG_NUM|>#2 = 7654321
用户：  把这两个加起来
答案：  <|PKG_NUM|>#1 #2        ← 不是"1234567 和 7654321"这串明文
```

**这一步把指代消解从开放生成变成了受限分类 + 组合选择，于是可以全自动判分。** 这是包引用方案对"测代词"的直接贡献：以前没法量化，现在有严格/部分两档分。

### 1.8.2 为什么这和 Transformer 架构有关

指代消解需要三种能力，每一种都有明确的架构依赖：

| 能力 | 架构依赖 | 小模型的风险点 |
|---|---|---|
| **跨位置检索**：从"这两个"回看到 A、B 的位置 | attention 的跨度 | 距离越远越难；4 层模型的注意力能覆盖多远是**经验问题** |
| **数量约束**："两个"要求恰好选 2 个 | 计数能力 | v4-A 已实测：计数依赖逐位复制，宽了会错 |
| **干扰排除**：前面有 5 个候选，是最近两个还是特定两个 | 选择性 | 干扰项多时易选错 |

这三种能力**不能靠猜**。而且它们有一个共同的上限：**投影能有多长**。因为投影本身就是一段带包引用的上下文，模型要在里面找到正确的引用——这和代词消解是同一个操作。

### 1.8.3 实验设计：三轴梯度探针（不依赖完整协议）

这个实验可以**独立于协议单独做**，只需要前端（已有）+ 合成数据 + 交流基座。

| 轴 | 取值 | 测什么 |
|---|---|---|
| **距离** | 10 / 50 / 100 / 200 / 400 token | attention 跨度上限 |
| **干扰项数** | 2 / 5 / 10 / 20 个同类型候选 | 选择性 |
| **类型混淆** | 干扰项与目标同类型 / 不同类型 | 类型标记（`<\|PKG_NUM\|>`）是否真的起作用 |

因变量：引用选择的精确匹配率 + 部分匹配率（同 04f 的双档判分）。

**样本构造**：程序生成，不需要人工。给定目标引用集合，在其前面插入 N 个干扰项、控制距离，代词短语从封闭池里选（"这两个"/"它们"/"上面那两个"/"刚才那两个数"…）。

**预期产出三个可用的数字**：

1. **距离-准确率曲线** → 决定投影最长能写多少 token（这是协议设计参数，不是猜测）
2. **干扰项-准确率曲线** → 决定投影里包表要不要截断、要不要按相关度排序
3. **同类型 vs 不同类型对比** → 验证 `<|PKG_NUM|>` 这种类型标记到底有没有帮模型区分

### 1.8.4 实测结果（2026-10-21，65M / 4 层 / 352 条 / 30 epoch）

**结论**：代词能力**存在**，但当前数据量不足以下最终结论。

| 指标 | 数值 |
|---|---|
| 距离轴 10→400 token | **全 1.00**，未观察到衰减 |
| 干扰项 2 / 5 | 1.00 |
| 干扰项 10 | 0.94 |
| 干扰项 **20** | **0.81**（首次明显下降） |
| 类型混淆 同 / 异 | 1.00 / 1.00 |
| **目标在末尾组**（只数末尾也能对） | n=87，**0.989** |
| **目标不在末尾组**（必须读代词） | n=265，**0.974** |

**关键判据**：末尾组与非末尾组几乎无差（0.989 vs 0.974）。这说明模型**确实读了代词里的序数并定位包**，不是"数包表末尾"。

这个判据不是白设的：**v1 数据上它完全不成立**（v1 目标恒在末尾，A 100% / B 0%，输出是 `<|OUTPUT|> #11 #11 #11 #1` 纯末尾序号）。改成"目标位置随机 + 代词带序数"之后行为变了，所以修数据是有效改动。

**必须标注的证据边界**：

1. 这 352 条里 **282 条是训练集、仅 70 条是 val**。上面数字含训练集，**不是泛化分数**。
2. 距离轴到 400 token 全对，但这只是同分布内。真正跨度上限要单独统计 val 并扩到 800/1600。
3. 干扰项 20 掉到 0.81，是目前唯一观察到的真实边界。
4. 类型混淆两组都满分，**测不出差异**，不能据此说"类型标记有用"。

**三个可用的初步数字**：

| 数字 | 当前值 | 用法 |
|---|---|---|
| 投影长度 | ≥400 token 可用（未探到上限） | v1 投影可放心写到 400 token |
| 干扰项上限 | 10 个安全（0.94），20 个开始出错（0.81） | 包表超 10 项需排序或截断 |
| 类型标记 | 未见混淆，但也未证有效 | 需设计"去掉标记会出错"的对照 |

**下一步必须补的三件事**：只报 val 分数（或扩数据做 held-out）；距离轴扩到 800/1600 找衰减点；类型混淆改造成能测出差异的对照。

### 1.8.5 三种可能的失败，对应三种修法

| 现象 | 说明 | 修法 |
|---|---|---|
| 近距离高、远距离崩 | attention 跨度不够 | 缩短投影；或按相关度把候选排到前面 |
| 干扰项一多就崩 | 选择性不足 | 训练数据里加大干扰项比例；或先 `ASK` 澄清 |
| 同类型与不同类型一样差 | 类型标记没被用上 | 投影里显式加类型词；或换标记位置 |

**这个实验的结论会同时决定两件事**：交流基座需要多大规模、投影格式必须多紧凑。所以它应该排在模板训练之前做——否则投影格式定完再发现模型看不了那么长，要返工。

## 8. 状态投影的文本格式是真难点

总册列为"开放点 2"。同一份状态，`[包] <|PKG_NUM|>#2 数值(来自#1)` 和一句中文描述，小模型表现可能差很多。这个必须先小样本试错定稿，不能靠猜。

### 8.1 投影格式还多了一个新约束（这次纠正带来）

投影的读者**已经不是同一个模型了**。门诊写的投影要给声明科医生读，声明科写的要给算数科医生读。这些是不同权重，各自在续训中形成不同的分布偏置。

后果：**投影格式必须在所有医生的训练数据里逐字一致**，不能各科室自己微调措辞。这条如果做不到，跨模型交接会在训练阶段就悄悄错位，而且很难从 loss 上看出来。
