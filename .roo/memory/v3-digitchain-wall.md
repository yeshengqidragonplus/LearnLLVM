# v3 核心发现：墙从"复制丢位"转移为"位数不可知"（2026-09-18）

## 现象（v3 实测，`V3_SUMMARY.md`）
5 位以上全部 0%，但**失败点在位数而非复制**：
```
问: s(97443) = ?（5位）
→ 理解: 算式 F, F := s(x), x := 9,7,4,4     ← 只输出 4 个数字
→ 算法: ... i 从 1 到 4 循环                 ← 循环上界 4（应 5）
→ 后续逐位执行、进位、合成全对（机制没问题）
```
同一病在四处复发：5/6/7 位后继、5/6/7 位加法、`38310=`万级读法（丢"三万八千"）、
`s(s(1400))`（丢成 140）。

## 结论
- 循环计数格式（`i=1..k`）**执行机制正确**（3/4 位 100%），但它**假定 k 已知**
- **"位数"从未被显式训练**——它是训练数据的隐含属性（1~4 位随机采样）
- 所以 v3 的墙 = "模型产生不出数字 5 作为位数"（训练范围 1~4 的硬边界）
- v4 方向：新增**显式"数位数"**目标（`问: 97443 是几位数?` → `计数: i=1..5` → `答: 5`），
  且数位数自身也要宽度无关（数 20 位就是数到 20）

## 序关系方向语义丢失（独立问题）
`问: 5503<5497?` 应 ⊥，模型自动从 min(5497) 数到 max(5503) 答 ⊤。
根因：`order_chain()` 内部 `lo,hi=min,max` 统一从小的数起数，
模型**从未见过"从 a 出发只会越来越大（不可达）"**的样本。
修法：训练数据包含"从 a 出发"的完整尝试链 + 结论 ⊥。

## 工程：OOM 与分块 loss（可复用）
- 根因：HF 把 logits 升 fp32，`batch×seq×vocab(151646)×4`；v3 序列 305 vs v2 188 → 2.96GB
- 精度实测：bf16 算 loss 梯度误差 1.35%；fp16 范围小需 scaling
- 解法：`03_train_pretrain.py --loss-chunk 64`（分块 fp32，对拍相对差 0.0000%，数学等价）
  + `--verify-loss` 对拍开关。附带提速（5596s 完成，原预估 7h）。
