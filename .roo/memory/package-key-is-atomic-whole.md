# 包 key 必须是原子整体：`<|PKG_NUM|,#3>`（2026-10-22 用户纠正）

用户明确指出我之前把包拆错了形态。核心原则原话：

> 你要能把包做成一个整体，不要再让大模型理解意思了，就整体是个包就可以了，
> 并且知道包和包 key 不同就是不同的意思就够了，拆包的时候能根据类型和值还原回去，
> 给专家模型处理。这是核心思想。

## 正确形态 vs 我的错误形态

| | 形态 | token | 问题 |
|---|---|---|---|
| **正确** | `<\|PKG_NUM\|,#B>` | **1**（注册后） | 类型与序号在同一个尖括号内，不可再分 |
| 错误1 | `<\|PKG_NUM\|>#B` | 3 | 序号游离在标记之外，`#`/`B` 是普通 token，会与上下文任何同形字符混淆 |
| 错误2 | `<\|PKG_NUM\|>#B 数值(#B)` | 8 | 编号重复两次，一个整体被拉成 8 段，其中 5 段纯冗余 |

**注册实测**：`<|PKG_NUM|,#B>` 加入 special_tokens 后是 **1 个 token，ID 唯一**。
6 类型 × 26 序号 = 156 个 key。22 项包表 = **22 token**（旧形态是 176 token）。

## 为什么这个原则决定实验设计

模型**不需要理解包内容**，只需要知道「key 不同 = 意思不同」。所以：

1. **包表里的每一项就是一个 token**。测「模型能同时把握多少个包」时，单位是 token 数，
   不是被撕碎后的字符噪声。用旧形态测出来的「22 项掉到 0.94」不可解释。
2. **类型标记必须绑在 key 里**。分开写就等于把类型信息退化成「要读 # 后面那个字母才猜到」，
   `type_confusion` 轴测的东西完全变味。
3. **拆包靠程序按类型+值还原**，交给专家。这是 token filter 机制本身，不是模型能力。

## 已作废的结论（勿引用）

下面这些记录建立在「裸编号 + 冗余条目」的错误数据形态上，结论不可信：

- `README.md` 3.10.1 / 3.10.2（编号改字母的对照实验）
- `data/pronoun_probe_v1_report.json` 的 `id_scheme_experiment` 一节
- `.roo/memory/package-ref-single-char-id.md` 中「包表 10 项上限是真实容量限制」的结论

原因：那两个分支（数字编号 / 字母编号）**都**丢掉了 key 的整体性，
所以「换编号后分数没变」只能说明两种错误写法一样坏，不能推出容量上限。
