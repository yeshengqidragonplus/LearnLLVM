# 探针设计陷阱：把「数位置」当成协议需求（2026-10-22 用户纠正）

代词探针做了 6 个版本，最后被用户一句话推翻设计：

> 如果只是做输出，直接用工具把 `<|PKG_NUM|,#A>` 替换成 A 输出即可；
> 如果要实际运算，A 是实际运算的推导变量，这个等训练数学专家的时候再说，
> 所以不应该出现位数或者数量规模问题。

## 错误：用序数代词测「能力边界」

v1~v6 的轴都用「第几个和它后面那个」这种**序数代词**，要求模型在 N 个同质 key 里
数到第 N 项再取两个。于是得到「包表超过 12 项就挑不准」（22 项 0.9375、留出 0.50）。

**但这个能力协议里根本用不到。** 模型只需知道 `<|PKG_NUM|,#A>` 是一个数字包；
值在缓存里，程序按 (类型, 序号) 解包交给专家。**包排在第几、值是多少，都不需要模型知道。**

所以那个「12 项上限」测的是自造的题目，不是协议的能力边界。**已作废。**

## 重设计（v7）：三条轴都不含序数

| 轴 | 题目 | 测什么 |
|---|---|---|
| `type_id` | 给一个 key，说出它的类型 | 是否真懂 key 的类型前缀（token filter 前提） |
| `semantic_pick` | 包表里**只有一个 NUM**，其余是其他类型；按「那个数值」选出它 | 按类型定位，**不数位置** |
| `distance` | 同上 + 无关填充到 800 token | 投影能写多长 |

审计硬断言两条，缺一不可：
- `num_key_unique`：NUM 包必须唯一，否则「那个数值」有歧义，题目不成立
- `no_ordinal_in_pronoun`：代词里不许出现序数，否则又退化成效数位置

## v7 结果

| 轴 | 同分布 | 留出（102 条） |
|---|---|---|
| semantic_pick 干扰 2/5/10 | **1.00** | **1.00** |
| semantic_pick 干扰 20（21 项） | 0.97 | 0.86 |
| distance 10→800 | **1.00** | **1.00** |
| type_id 六类型 | 0.88~1.00 | **0.25~1.00** |

**结论：语义指代可用且与候选个数基本无关；投影可写到 800+ token。**

## type_id 失败是配比问题，不是机制问题（v8 已证实，2026-10-23）

留出集错误几乎全部把答案吐成 `<|PKG_TASK|>`（CODE→TASK、ARITH→TASK、NAME→TASK）。
`type_id` 只占 192/512 条，答案又是单 token 开集生成 → 6 个类型标记喂不饱，坍缩到一个。

**这不证明「类型标记无效」，只证明这份配比训练不足。** 要下结论必须改成选择题
（给 2~6 个候选类型选一个）并把 type_id 提到总量一半以上。

v8（`24/25` 号，672 条，type_id 提到 300 条）证实了这条推断：

| 档 | 留出严格分 |
|---|---|
| 给 2 个候选 | 0.97 |
| 给全部 6 个候选 | 0.97 |
| **不给候选（= v7 形态）** | **0.94** |

三档只差 4 个百分点，所以**候选枚举不是必需的**，协议里可以要求开集输出类型标记。
v7 的 0.25~1.00 纯粹是样本量不够。详见 `.roo/memory/atomic-key-zero-shot-is-zero.md`。

## 通用教训

设计任何探针前先问：**「这个能力在协议里真的会被用到吗？谁来做这件事——模型还是程序？」**
如果答案是程序（如解包、数位置、拼载荷），就不要拿它去测模型的边界。
