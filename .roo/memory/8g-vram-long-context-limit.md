# 8G 显存 + 65M 模型的长上下文实测上限（2026-10-21）

指示代词探针 v3 扩了距离轴到 800/1600，训练反复失败。实测定位到硬边界，
并得出 `MAX_SEQ_LEN` 的推荐值。

## 实测（batch=8、loss-chunk=64、hidden 384 / 4 层、BF16、RTX 4060 Laptop 8188 MiB）

| 序列长度 | 峰值显存 | 占卡 | 单步耗时 | 倍数 |
|---|---|---|---|---|
| 414 token | 3106 MiB | 37.9% | 0.19 s | 1.00x |
| 824 token | 5170 MiB | 63.1% | 0.33 s | 1.77x |
| 1624 token | **9440 MiB** | **115.3%** | **6.22 s** | **33.5x** |

固定开销仅 391 MiB（BF16 权重 125.5 + AdamW 状态 265.5），**瓶颈全在激活**，与参数量无关。
线性拟合（安全侧）：激活 ≈ 548 + 5.23 × L (MiB)。

推算：512 token = 3619 MiB (44.2%)｜1024 = 6299 MiB (76.9%)｜1150 = 6958 MiB (85%)。

## 关键坑 1：Windows 显存超限不报 OOM，而是静默换页

1624 token 超限 1252 MiB 后，WDDM 把显存换页到系统内存，**不抛 OOM**：

- 耗时 0.33 s → 6.22 s（33.5x；纯 attention O(n²) 应只 15.4x，多出的 ~2x 是换页）；
- 该路径在 BF16 下产生非有限值 → `train_loss nan`（实测一轮 2443 s 后 train/eval 双 nan）；
- `clip_grad_norm_` 再把 nan 扩散到**全部 50 个张量**，保存出的 checkpoint 全废
  （实测 epoch01 的 58,237,440 个 embedding 元素全 nan）。

排查走过的弯路：先用 safetensors 检查 epoch03 权重（干净）→ 逐 47 batch 前向+反向
（全部有限、logit_absmax 稳定 12.0）→ 离线复现完整 9 epoch 378 步（全有限、loss 0.71→0.006）
→ 最后才靠「epoch 耗时 6.8 倍 + GPU 空闲重跑后 loss 恢复正常 0.259」定位到显存/抢卡。

**若再遇到「权重干净但训练出 nan」，先看 nvidia-smi 的 memory.used 和单 epoch 耗时倍数，
不要先怀疑 lr 或数据。** 另注：环境里常有 10 个 `Unity.exe` 抢卡，跑长上下文前必须确认 GPU 空闲。

## 关键坑 2：`MAX_SEQ_LEN` 在 `--no-pack` 下不截断序列

`03_train_pretrain.py:42` 的 `MAX_SEQ_LEN = 512` 只写进 config 的
`max_position_embeddings`，no-pack 路径按数据实际长度送模型（v3 最长 1639 token）。
所以**改这个值不会让长样本变省显存**，它只决定 RoPE 外推倍数。

## 推荐值：`MAX_SEQ_LEN = 1024`，删掉 1600 档

- 512 显存完全够（44%），但距离轴 800 档需 818 token、1600 档需 1615 token，
  512 只够覆盖到 400 档——而 v1/v2 已在 400 全 1.00 未探到上限，用 512 等于作废本次扩展。
- 1024 覆盖 800 档（818 token）有余量，842 token 实测 64%，1024 上限推算 77%，留 1889 MiB，
  不进换页区；RoPE 外推 2x，而 Qwen2 的 `rope_theta=1000000`（默认 10000 的 100 倍）本就为长上下文设计。
- 探针是 `init_from=null` 从零训练，改 `MAX_SEQ_LEN` 无重新训练基座的负担。
- 若要更保守可用 896（覆盖 850 token，68.7%，外推 1.75x）。
- **1600 档在 8G 上不是调参能解决的**：同时撞显存（115%）与位置编码（外推 3.2x）两道墙。
  若必须保留，需降 batch 到 4（约 4920 MiB）并把基座 `MAX_SEQ_LEN` 训到 ≥2048。
