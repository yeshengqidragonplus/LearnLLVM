# 包表容量上限：三重独立验证都指向「项数」（2026-10-22）

用户纠正了两个形态错误后，重做了三次对照。**三次结果完全一致**，因此这个结论
现在有三组独立数据支持，可归因。

## 三次实验（同一模型配置 65.32M / hidden 384 / 4 层，30 epoch）

| # | 包表条目形态 | 包表 22 项占 token | 同分布 strict | 留出 strict |
|---|---|---|---|---|
| 1 | `<\|PKG_NUM\|>#22 数值(#22)` + 数字编号 | **258** | 0.9375 | 0.50 (n=4) |
| 2 | `<\|PKG_NUM\|>#V 数值(#V)` + 字母编号 | **~200** | 0.9375 | 0.50 (n=4) |
| 3 | `<\|PKG_NUM\|,#V>` + 原子 key | **79** | 0.9375 | 0.50 (n=4) |

**准确率一字未变，而 token 数差 3.3 倍。** 这是关键：

- **不是 token 长度问题**（79 token 远够用，距离轴 815 token 仍满分）
- **不是编号形态问题**（数字/字母/原子 key 三种写法同分）
- **是候选项数问题**：22 项开始超出选择性能力

## 结论

| 干扰项数 | 包表项数 | 同分布 |
|---|---|---|
| 2 / 5 / 10 | 4 / 7 / 12 | 1.00 |
| **20** | **22** | **0.9375**（留出 0.50） |

真实阈值落在 **12~22 项之间**，尚未定位。要收窄需把 level 加密到 14/18/22
并扩大每格样本量（现在留出集的 level=20 只有 4 条，单条波动 25%）。

## 原子 key 形态（用户纠正后的正确写法）

一个包 = 一个不可分的整体 key：`<|PKG_<TYPE>|,#<ID>>`，注册后 **1 token**。
- 类型与序号在同一个尖括号内，模型不需要理解内容，只需区分 key 是否相同
- 载荷由程序按 (类型, 序号) 从缓存解包，交给专家模型
- tokens.json 的 `_package_keys`：6 类型 × 26 序号 = 156 个，id_base=151660
- 03 号用 `--package-keys` 注册；22/23 号各自断言单 token + ID 与 tokens.json 一致

## 另一个真正的收益：投影变短了

包表 22 项从 258 token 降到 **79 token**，整个 22 项样本的 context 只有 79 token。
这不是"为了分数"，而是协议本身的正确形态——投影不必为了容纳 22 个包而膨胀。
