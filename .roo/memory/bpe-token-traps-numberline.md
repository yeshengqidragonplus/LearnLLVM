# BPE 切分陷阱与评估通道污染（数轴实验，v7.2/v8 实测）

Qwen2 tokenizer 对**多位数是逐位切分**的：`357`→`['3','5','7']`，`1000`→`['1','0','0','0']`，
10~99 的 90 个两位数**没有一个**是单 token。所以位值递推在表示层完全可行，
数轴学不会**不是 tokenizer 的锅**。

## 陷阱一：空格 + 负号被合并成 `Ġ-`
`-9 -8。` → `['-','9','Ġ-','8','ãĢĤ']`。空格被 BPE 并进后继的负号。
后果：prompt `-9 `（尾空格）切出 `['-','9','Ġ']`，末尾裸 `Ġ` 这个状态
**在训练里从未出现**（负数的后继仍是负数，空格永远被合并），模型被推进分布外。
=> 负数后继的 prompt **不能加尾空格**；正数后继可以（`7 8。`→`['7','Ġ','8','ãĢĤ']` 不合并）。
同类已知陷阱：v7.1 的 `=-` 合并（负结果必须写 `= -X`）。

## 陷阱二：裸数字 prompt 的 next-token 通道被高频任务压死
实测 v7.2（`check_ambig_tmp.py`）：
```
'-9'  -> '小于':0.563 | '大于':0.341 | ' -':0.081    <- 比较句压死相邻对
'7'   -> '+'   :0.451 | '-'   :0.374 | '大于':0.089  <- 算式压死相邻对
'-9 ' -> '8'   :0.873                                <- 只有尾空格能救正数
```
根因是**频次比**：v7.2 比较句 10100 条 vs 相邻对 408 条 = **24.8 : 1**。
负数无法用尾空格消歧（见陷阱一），所以 v7.2 负数后继必然 0%。
=> 解法：加任务标记 `后继 a b。`。实测 `后继 a` 对正负数都是 `后继 a a+1。`
的严格 token 前缀（8/8 通过），且与比较句/算式完全不共享前缀，歧义从根上消除。

## 陷阱三：04h_eval_math_v7.py 的 [A] 项是假测试
```python
out = gen(f"{a} {b}")              # 答案 b 被喂进了 prompt！
good = out.startswith(f"{a} {b}")  # 实际只测"能否补出句号"
```
这解释了为什么 04h 报 `[A] 数轴相邻对 60/60 = 100%`，而 `04i_probe_successor.py`
一测外推就全崩（`51`→`'4'` p=0.985）。**那个 100% 从未测过数轴能力。**
=> 评估 prompt 只能给 `a`，答案必须由模型自己生成。用 `04l_eval_numberline.py`。

## 通用防线
任何新评估脚本都必须先做 **prompt 前缀一致性自检**：
`tok.encode(完整训练样本)[:len(prompt_ids)] == prompt_ids`。
不通过就直接报错退出，不要出分数——否则测的是脚本 bug 而不是模型能力。
`04l_eval_numberline.py` 的 `[S0]` 段就是这个自检的参考实现。
