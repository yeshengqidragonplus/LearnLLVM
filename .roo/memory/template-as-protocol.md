# 「模板即协议」：模板思路与 token filter 是同一件事（2026-10-21）

用户认为我之前自造的「【追问】/【挂号】/【转诊】」模板**是个好思路**（待他考虑）。
复盘后确认：模板思路本身没错，错在实现方式。两者的本质完全同构：

| | token filter（已成功 12/60→58/60） | 模板话术（首版失败） |
|---|---|---|
| 模型输出什么 | 静态标记 `<|PKG_NAME|>`，不复制载荷 | 静态标记 `【追问】`，但**字段值仍是明文** |
| 载荷在哪 | 缓存，程序解包 | 直接拼在回答里（科室名、表达式、代码） |
| 结果 | 58/60 严格 | 退化成复读「第一/第二/最后」 |

**关键结论：模板 = 给定有限动作空间 + 静态标记输出。这正是 token filter 成功的原因。**
首版模板数据失败的真正原因是两处：

1. **字段值没打包** —— `科室=算数科｜表达式=1234567+7654321` 里的算式是明文，
   又回到了逐字符复制问题（和 target 未打包完全同一个 bug）。
   正确做法是 `科室=<|DEPT|>｜表达式=<|PKG_NUM|>`，值进缓存，程序解包。
2. **数据里没有真实对话内容**，只有模板骨架，模型只能学到"复读骨架"。

所以模板要成立，必须同时满足：
- 动作/字段名用静态标记（`【追问】`、`<|DEPT|>`），值一律走原子包；
- 样本里带真实业务内容（真实算式、真实代码、真实语言名），而且这些内容也要打包；
- 多轮样本必须体现"用户补充 → 状态变化 → 下一步动作"的因果，不是并列罗列。

这条把「部分③ 拆解+循环」的设计方向也定住了：**每一步的动作行也必须
是"静态标记 + 原子包引用"，不能是自由文本**，否则每步都要复制上一步结果，
必然重演复制墙。
